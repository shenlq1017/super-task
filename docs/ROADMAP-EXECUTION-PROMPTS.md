# Roadmap 方向执行提示词

> 本文是给 AI 编码代理使用的执行模板，不是新的功能规划。
> `docs/ROADMAP.md` 负责方向与可行性，`docs/spec/` 负责当前行为契约，
> 本文负责把一个方向推进成可验证的最小交付切片。

## 使用方式

每次只复制“通用执行协议”和一个方向的任务块。若本轮已经确定了具体候选项，
把任务块中的“建议首个切片”替换为实际切片；没有确定时，让 AI 先基于代码证据选择一个最小纵向切片。

不要把一个方向的所有候选项一次性塞给 AI。每个切片都必须独立完成、独立验证，
并在下一轮根据实际结果重新选择优先级。

默认优先使用“一轮自动执行模式”：用户只发送一次提示词，AI 在内部完成计划、实现和验证；
只有高风险、需要用户确认或一次切片仍然过大的任务，才退回分阶段模式。

## 一轮自动执行模式

一轮模式不是取消阶段，而是把阶段切换交给 AI。AI 仍按 `Plan → Contract → Core → Adapter/UI → Verify`
顺序工作，但不要求用户在每个阶段之间手工发送提示词。阶段之间只保留短检查点，最终一次性报告。

适合一轮模式的条件：

- 只推进一个候选项或一个最小纵向切片，而不是整个方向。
- 核心目标、验收条件和安全边界可以从 roadmap、spec 和现有代码中确定。
- 不需要用户在中途决定产品取舍，不涉及不可逆的外部操作。
- 受影响模块数量有限，能够用聚焦测试证明结果。

一轮模式的硬限制：

- 先做短计划再编码，但计划只保存在 `.zcode/local/roadmap-plans/`，不把整段探索过程输出到对话。
- 只读取与当前切片直接相关的文件；当前事实最多记录 10 条，命令输出只保留摘要、路径和结果。
- 每个内部阶段最多 1–3 个紧密任务；可以跳过不适用的阶段，但必须记录“跳过及原因”。
- 不自动实现第二个候选项，不因为发现顺手问题而扩大范围，不重复已经交付的能力。
- Plan 不跑长测试；Contract/Core 跑过滤测试；Adapter/UI 只做必要构建检查；Verify 才扩大回归。
- 每个阶段结束都更新检查点；若计划失效、出现错误循环、需要高风险决策或范围明显变大，安全停在当前阶段并报告，不为了凑成“一轮完成”而强行修改。

单轮模式的推荐提示词：

```text
请在一个连续任务中自主完成下面指定的一个最小路线图切片，不要要求我在阶段之间手工确认。

目标方向：<方向名称>
本次切片：<一个候选项或明确的最小纵向切片>

执行方式：
1. 先阅读 AGENTS.md、相关 roadmap/spec、现有实现和测试，做一个短计划；不要先改代码。
2. 将内部工作分成 Plan、Contract、Core、Adapter/UI、Verify 阶段，按顺序自动执行。
3. 只读取当前阶段需要的文件，不重复扫描全仓库，不输出整段源码、完整日志或全量测试输出。
4. 在 `.zcode/local/roadmap-plans/<direction>-<slice>.md` 保存计划和每阶段检查点；检查点只记录事实、改动、验证结果、未决项和下一步。
5. 每阶段最多完成 1–3 个紧密任务；不适用的阶段跳过并写明原因，不得实现计划外候选项。
6. 先运行便宜的聚焦检查，再修改，再运行该阶段验证；最终 Verify 再运行必要的模块/仓库级检查。
7. 遵守 AGENTS.md：业务逻辑进 supertask-core，src-tauri 保持 IPC 薄适配，前端不直接 shell/fs，测试离线，秘密不进日志、事件或返回值。
8. 发现计划与代码事实冲突时，先更新检查点并收缩范围；只有需求冲突、不可逆操作或缺少关键产品决策时才停止并提问。
9. 最终只输出：结果、修改文件、每条验证命令及结果、未运行项及原因、当前状态、计划文件路径和仍未覆盖的范围。

只有最终 Verify 的完成条件全部有证据时，才能宣布该切片完成；不要把“已修改代码”当成完成。
```

一轮模式仍可能因编译、真实环境或跨平台问题耗时较长，但它会把重复探索和阶段间人工搬运降到最低。
如果单轮任务持续出现长时间测试、错误循环或上下文再次膨胀，应保留检查点并退回分阶段模式，而不是继续追加提示词。

## 方向五的一轮提示词

方向五当前最适合一轮完成的切片是“将已有 `system.metrics` 通过 MCP 暴露为结构稳定、只读且脱敏的工具”。
下面这段可以直接作为一次用户消息发送：

```text
请在一个连续任务中完成 SuperTask 路线图方向五的首个最小切片，不要要求我在阶段之间手工确认。

目标：把已有 system.metrics 通过 MCP 暴露为一个结构稳定、只读、脱敏的主机指标工具。

明确不做：历史趋势持久化、按服务资源归因、完整体检报告、第二套指标采样器、任意 shell 或原始日志暴露。

请自动完成以下内部阶段：
- Plan：阅读 AGENTS.md、docs/ROADMAP.md、docs/ROADMAP-NEXT-SLICES.md、docs/spec/、现有 system.metrics、MCP/CLI 注册入口和相关测试；确认事实和影响文件。
- Contract：确定工具输入、输出、单位、采样时间、平台字段、缺失值、错误和只读语义。
- Core：复用现有 system.metrics，完成结构化映射、异常处理和脱敏，不重复实现采样器。
- Adapter/UI：注册 MCP/CLI 工具；只有现有入口确实需要时才接 IPC/UI，前端不得直接读取主机数据。
- Verify：运行受影响 crate 的聚焦测试、必要构建和格式检查，审查 schema、跨平台行为、只读性、脱敏和 git diff。

执行约束：
1. 先做短计划再编码，并将计划和检查点保存到 .zcode/local/roadmap-plans/observability-system-metrics-mcp.md。
2. 阶段之间自动继续，不要向我索要确认；每阶段最多 1–3 个紧密任务。
3. 只读取当前阶段需要的文件，不重复扫描全仓库，不输出完整源码、长日志或全量测试输出。
4. Plan 不跑长时间全量测试；Contract/Core 只跑过滤测试；最终 Verify 才扩大回归。
5. 所有测试离线；不得把 token、密码、连接串、环境变量或原始进程信息放进 MCP 输出、事件、日志或审计记录。
6. 若计划与代码事实冲突，先收缩范围并记录；不要实现方向五的其他候选项。
7. 如果某个阶段确实不适用，跳过并说明原因；如果出现高风险决策或不可安全继续，保存检查点并报告未完成，不要强行扩大范围。

最终只报告：实现结果、修改文件、验证命令和结果、未运行项及原因、当前状态、计划文件路径和未覆盖范围。
只有最终 Verify 的验收条件全部有证据时，才能宣布切片完成。
```

如果切片不满足一轮自动执行条件，再使用分阶段执行：

1. 第一轮只执行“计划阶段提示词”，只读代码和文档，产出本地计划，不改业务代码。
2. 后续每轮执行“执行阶段提示词”，只完成计划中的一个阶段，并在阶段末写检查点。
3. 检查点完成后结束当前轮次；下一轮只读取计划文件、相关文件和上次验证结果。

单文件、无行为变化且预计很快完成的任务可以跳过计划阶段。计划不是为了增加仪式，
而是为了让高风险或过大的切片可停止、可恢复、可验证；普通切片优先使用上面的一轮模式。

## 为什么要分计划和执行

单个方向耗时过长，通常不是代码本身需要一个小时，而是同一任务同时承担了全量探索、架构决策、
多批实现、全量测试和反复回看上下文。计划阶段能提前固定范围，检查点能避免下一阶段重走探索；
但计划本身也必须有边界，否则会变成另一种上下文膨胀。

推荐的阶段边界如下：

| 阶段 | 允许做什么 | 必须产出 | 结束条件 |
|---|---|---|---|
| Plan | 阅读目标相关文件、确认现状、拆任务、找风险 | 本地执行计划 | 计划可由另一个新会话直接执行 |
| Contract | spec/schema/错误码/类型和测试契约 | 契约变更与测试形状 | 字段、兼容性和失败语义明确 |
| Core | 一条核心业务链路 | core 实现和聚焦测试 | 核心行为可独立验证 |
| Adapter/UI | IPC 薄适配和必要 UI | IPC/UI 接线与测试 | 端到端入口可用 |
| Verify | 聚焦回归、格式、构建和 diff review | 验证记录与检查点 | 完成条件全部有证据 |

默认每轮只做一个阶段，或最多做同一阶段内 1–3 个紧密相关任务。不要在一次轮次中自动跨过
Contract、Core、Adapter/UI 和 Verify 四个边界。

## 计划文件与上下文预算

计划文件放在 `.zcode/local/roadmap-plans/<direction>-<slice>.md`，该目录已被 git 忽略，
不会污染产品文档。`docs/ROADMAP-NEXT-SLICES.md` 只记录方向切片和验收雏形，不替代执行检查点。
AGENTS.md 中出现的 `.workbuddy` 仅指历史本地存档；本轮执行计划和检查点统一使用 `.zcode`。
默认在同一工作目录的后续轮次继续；如果切换到新的 Git worktree，忽略文件不会自动带过去，
必须把计划摘要粘到下一轮提示词，或经用户同意后写入仓库内的任务文档，不能假设计划仍然存在。

计划文件只保留决策所需的信息：

- 当前事实：最多 10 条，带 `file:line` 证据
- 目标、非目标和验收条件
- 依赖与风险：只记录会改变实现路径的风险
- 阶段清单：每阶段 1–3 个任务、输入、输出和验证命令
- 检查点：已完成、验证结果、失败/未决项、下一阶段

不要把整段源码、完整日志、全量测试输出或整篇 spec 复制进计划。输出过长时只记录摘要、命令、
结果和文件路径。每个阶段开始时优先读取计划和上次检查点，再按计划定向读取文件；发现计划失效时先更新计划并停止扩张，不要边做边默默改变范围。

验证也分层执行：Plan 不跑产品测试；Contract/Core 只跑受影响 crate 的过滤测试；Adapter/UI 只做
必要的类型/构建检查；最终 Verify 再跑仓库级回归。涉及共享契约、安全边界、并发运行时或跨平台代码时，
可以提前扩大验证范围，但必须说明原因。若一次会话已经跨越两个阶段或积累了大量工具输出，先写检查点，
再使用 `/compact` 或新的执行轮次继续，不要为了保持连续性保留整段历史。

## 计划阶段提示词

```text
这是一个复杂路线图切片，请先只做计划，不修改业务代码，不运行长时间的全量测试。

1. 阅读 AGENTS.md、docs/ROADMAP.md、docs/ROADMAP-NEXT-SLICES.md、目标方向块，以及与本切片直接相关的 docs/spec/、实现、测试和示例。
2. 用代码和文档证据确认当前事实，不把 roadmap 的“现状”当作未经验证的真相。
3. 将切片拆成 Contract、Core、Adapter/UI、Verify 阶段；每阶段最多 1–3 个紧密相关任务。
4. 为每个任务写出具体文件、依赖、输入/输出、完成条件、验证命令和停止/回滚条件。
5. 标出必须由用户决定的问题；其他问题根据仓库约定自行选择并记录理由。
6. 把计划写入 `.zcode/local/roadmap-plans/<direction>-<slice>.md`。

计划阶段禁止：修改产品代码、顺手修无关问题、为了“验证”运行全量构建/测试、把未来候选项加入本轮。

计划完成后只报告：计划文件路径、当前事实、阶段清单、风险、需要用户决定的问题（如有）和预计第一执行阶段。
不要在本轮开始实现。
```

## 执行阶段提示词

```text
按照 `.zcode/local/roadmap-plans/<direction>-<slice>.md` 执行指定的一个阶段：`<phase-id>`。

1. 先读取计划文件和上次检查点，只补读本阶段列出的相关文件；不要重做全仓库探索。
2. 开始前用不超过 10 行确认：本阶段目标、任务、非目标、验收条件和验证命令。
3. 只完成本阶段；不得自动进入下一个阶段，不得扩展到计划外候选项。
4. 先运行便宜的聚焦检查，再实现，再运行本阶段验证。只有共享契约、跨模块行为或最终 Verify 阶段才运行更大范围回归。
5. 发现计划与代码事实不一致时，先更新计划的风险/阶段，不要悄悄扩大实现范围。
6. 阶段结束时更新计划检查点：完成任务、修改文件、验证命令及结果、未决问题、下一阶段入口。

未满足本阶段完成条件或验证失败时，状态必须标为“未完成/阻塞”，不得宣布整个切片完成。
阶段检查点写完后停止，下一阶段由新的轮次继续。
```

## 通用执行协议

```text
你是 SuperTask 仓库的资深软件工程师。请推进下面指定方向的一个最小可交付切片。

工作顺序：
1. 若不存在计划文件，先执行计划阶段；复杂切片不得直接开始编码。
2. 若存在计划文件，只读取本阶段需要的上下文，遵守阶段边界和上下文预算。
3. 开始前说明当前事实、阶段目标、本轮非目标、影响文件、验收条件和验证命令。
4. 发现已有未提交改动时保留它们；不做无关重构，不凭空发明架构，不以 roadmap 文字覆盖当前 spec 契约。
5. 实施时遵守仓库约束：业务逻辑进 supertask-core，src-tauri 只做 IPC 薄适配，前端副作用走 IPC，安全边界和错误码保持稳定。
6. 行为变化必须同步更新对应 docs/spec/；需要时更新 schema、测试、CHANGELOG.md 和 docs/inventory/。
7. 先运行聚焦检查；只有阶段或风险需要时才扩大到模块/仓库级验证。所有测试保持离线，网络路径使用 fake transport。
8. 阶段结束必须更新计划检查点；最终 Verify 阶段才可判断整个切片是否完成。
9. 最后检查 git diff，主动寻找回归、遗漏的文档、无关修改、秘密泄露和跨平台问题。

只有在需求冲突、关键产品决策缺失或继续实施会明显扩大范围时才暂停提问；其他不确定性根据代码和文档证据自行决定并记录理由。

最终报告必须包含：
- 结果与仍未覆盖的范围
- 修改文件及关键行为
- 每条验证命令和实际结果
- 未运行的验证及具体原因
- 当前阶段状态（完成/未完成/阻塞）
- 计划文件和检查点位置
- 下一阶段入口（仅在当前阶段完成后给出）
最终 Verify 阶段未满足全部验收条件或未完成验证前，不要宣布整个切片完成。
```

## 方向一：服务监管与自愈

```text
方向目标：让每个服务都成为可持续托管的运行单元，能够按真实就绪状态纳入编排，
在启动、失败、重启和依赖变化时执行可预测的生命周期策略，并允许用户在异常后接管恢复。

建议首个切片：优先评估并实现日志模式就绪判定；若当前架构证据表明它不是最小切片，
选择同方向中下一个边界清楚的生命周期能力，并说明取舍。

本轮范围：
- 为服务健康/就绪模型增加日志模式这一种判定来源，或完成你选择的单一生命周期能力的端到端链路。
- 覆盖 YAML/spec、core runtime、错误处理和必要的 IPC/UI 显示。
- 保持 none/tcp/http、现有 restart 策略和既有清场行为兼容。

本轮不做：一次实现全部钩子、级联重启、手动重试和所有 ready 策略；不改变现有默认失败行为。

推荐阶段：
- Contract：确定 `log-pattern` 字段、匹配窗口、超时和状态迁移语义。
- Core：实现日志匹配与 ready 判定，先用 LogHub/假日志源覆盖边界。
- Adapter/UI：仅在现有状态展示无法表达新结果时接 IPC/UI。
- Verify：聚焦健康、重启和清场回归，再决定是否扩大测试范围。

完成条件：
- 配置的服务只有在满足明确的就绪条件后才报告 ready。
- 超时、进程退出、日志未匹配和配置错误都有稳定、可诊断的结果。
- 既有服务配置无需修改即可保持原行为。
- 新行为有 core 测试，并同步 yaml/spec/schema（如字段发生变化）。

验证重点：日志匹配边界、超时、重复日志、非 UTF-8/大日志输入、重启策略回归，以及秘密不进入错误或事件。
```

## 方向二：纳管任意来源

```text
方向目标：让本机已有的进程、Compose、Procfile、devcontainer 等服务来源都能先预览，
再以可追溯的方式纳入同一工作区拓扑，统一启停、健康检查、日志和冲突处理，而不是只能发现或终止。

建议首个切片：运行中进程原地接管的语义与权限边界；孤儿进程 dry-run 预览与确认写回已交付，
不要重复实现。先确定 attach 成功/失败和 Unix 降级语义，再接入实际接管。

本轮范围：
- 基于已交付的发现 preview/apply 结果，定义运行中外部进程 attach 的归属、权限和平台降级语义。
- 复用现有 Windows Job Object、DETACHED 会话注册和外部 PID 复核材料，完成一次不重启的接管链路。
- 让接管后的服务继续走现有停止、重启、健康和日志链路，并保留 attach 失败时的外部实例语义。

本轮不做：自动杀进程、无确认写回配置、任意环境变量原样回显、一次覆盖所有导入格式。

推荐阶段：
- Contract：定义 attach 状态、归属、权限失败和平台降级的 IPC/spec 语义。
- Core：实现进程接管、Slot 生命周期和 managed 状态转换。
- Adapter/UI：把“仅监控/已接管/接管失败”接入现有运行页，不传命令行。
- Verify：覆盖不重启、不误杀、停止/重启、重复接管和跨平台降级。

完成条件：
- attach 成功后进程不被杀、不重启，服务状态从“外部/仅监控”转为受管状态。
- 停止走正确的进程树清理，重启走完整引擎链路；attach 失败可诊断并回退。
- 重复 attach、PID 归属变化和进程退出不会误杀其他进程。
- Unix 不支持等价 attach 时，降级行为明确且不伪造受管状态。

验证重点：不重启接管、Job Object 权限失败、PID 归属复核、重复接管、停止/重启、Unix 降级和进程树安全。
```

## 方向三：环境供给

```text
方向目标：让工作区能够用声明式需求从已有环境、可用包管理器或免安装归档中补齐高频工具和中间件，
同时保持版本隔离、来源透明和失败可解释，使“从零准备并启动项目”成为可重复流程。

建议首个切片：免安装中间件归档供给执行器；`needs` 的 resolve-only/dry-run 与 mise/winget 供给已交付，
不要重复实现解析层，也不要一开始建设完整包仓库。

本轮范围：
- 复用已交付的 needs resolve 结果，选择一个高频中间件完成归档下载、校验、解压和可发现化。
- 供给器使用可测试的 fake transport/provider，明确下载计划、版本、来源、安装目录和项目隔离。
- 定义中断、重试、校验失败和回滚语义，避免把安装结果写成无法再次解析的隐式状态。

本轮不做：2000+ 包索引、无声明的全局安装、绕过权限或静默下载执行、一次支持所有工具链。

推荐阶段：
- Contract：确定归档目录、来源、sha256 清单、安装状态和错误码。
- Core：实现 fake transport 下的下载、校验、解压和沙箱检查。
- Adapter/UI：接入安装进度、重试和 PATH/解析结果；不把凭据传给前端。
- Verify：覆盖中断重试、zip-slip、校验失败、版本隔离、无网络和平台键。

完成条件：
- 相同目录、平台和版本得到确定的下载/安装计划，且能解释来源和选择原因。
- 下载成功后 sha256 校验、解压和 PATH/launcher 解析均可验证；已满足版本不重复安装。
- 安装路径和版本隔离符合 sandbox，中断后可安全重试，秘密和凭据不进日志。
- 归档供给器、needs 接口兼容性和失败路径都有离线测试。

验证重点：版本范围、平台差异、重复执行、provider 失败、路径越界、无网络测试和安装中断后的状态一致性。
```

## 方向四：网络与身份

```text
方向目标：让工作区服务在本机、局域网和受控的外部回调场景中都能稳定、可验证地访问，
统一处理域名解析、证书、反向代理、WebSocket、CORS 和隧道，同时不牺牲本地密钥与权限边界。

建议首个切片：本机 hosts 管理的 preview、冲突检测和权限错误契约；隧道纳管、网关 WebSocket、
重写/重定向/静态站点、CORS 和多域名别名已交付，不要重复实现。先完成 dry-run，再考虑系统写入。

本轮范围：
- 先实现 hosts 变更的纯预览、差异计算、冲突检测和权限错误契约，不立即写系统文件。
- 以 SuperTask 标记段为边界，明确幂等、关闭工作区清理和不触碰用户手工条目的规则。
- 复用现有路径校验与 IPC 约定，为后续受控写入保留稳定接口；不把写入权限下放到前端。

本轮不做：直接写入系统 hosts、提权子进程、私有 CA、完整 DNS 服务或其他网关能力；
也不重复实现已交付的隧道和路由功能。

推荐阶段：
- Contract：定义声明域名、SuperTask 标记段、冲突和无权限错误语义。
- Core：实现 hosts 解析、差异计算、幂等和只处理自有标记段的清理算法。
- Adapter/UI：增加用户确认和提权边界；UI 不直接写 hosts，实际写入须由受控 IPC 完成。
- Verify：先验证 preview/冲突/取消无副作用，再验证管理员路径和关闭工作区后的清理。

完成条件：
- preview 能展示新增、删除、冲突和不会触碰的用户条目，且重复生成结果稳定。
- 生成和清理只作用于 SuperTask 自有标记段；取消或无权限时不产生系统副作用。
- 域名冲突、非法地址和权限不足都有稳定错误码和明确恢复建议。
- 纯函数、IPC 合同和后续写入前置条件都有离线测试。

验证重点：hosts 标记段、幂等/冲突、用户条目保护、路径和域名校验、权限错误、取消无副作用及 Windows 行为。
```

## 方向五：主机与服务可观测性

```text
方向目标：把主机和服务运行状态变成可追溯、可归因、可供人和 AI 使用的诊断上下文，
能够回答“哪里在消耗资源、何时开始异常、当前是否适合启动新服务”，并提供可导出的体检结果。

建议首个切片：把现有 system.metrics 通过 MCP 暴露为一个结构稳定、只读且脱敏的工具。

本轮范围：
- 复用引擎已有指标采样，不重复实现第二套采样器。
- 定义主机指标工具的输入、输出、单位、采样时间和缺失值语义。
- 让 AI 能据此判断资源余量；必要时补充最小的 IPC 类型和测试。

本轮不做：一次实现完整历史数据库、复杂图表、所有服务归因和体检报告；不把原始进程环境或秘密暴露给 MCP。

推荐阶段：
- Contract：固定 MCP 工具输入/输出、单位、采样时间和缺失值语义。
- Core：复用现有 `system.metrics` 映射，不新建第二套采样器。
- Adapter/UI：先接 MCP；只有用户面板需要新数据时再接 IPC/UI。
- Verify：覆盖平台差异、空指标、敏感字段、只读性和 schema 稳定性。

完成条件：
- MCP 返回 CPU、内存、交换、磁盘、网络等已有指标，结构可被程序稳定解析。
- 指标包含时间/平台语义，缺失或不支持的字段不会伪造为零。
- 输出经过脱敏且只读，不触发启动、停止或文件写入。
- MCP、core 数据映射和异常路径有离线测试。

验证重点：单位和四舍五入、空指标、平台差异、并发读取、敏感字段扫描、MCP schema 稳定性和性能开销。
```

## 方向六：数据与备份

```text
方向目标：让与服务绑定的开发数据具备低门槛、可验证的快照与恢复能力，
支持工作区级定时保留和外部目录备份，同时通过纳管成熟工具满足数据库管理，而不自建完整数据库 GUI。

建议首个切片：基于现有归档机制实现一个服务绑定数据的快照/恢复最小闭环，先支持一个明确的数据来源。

本轮范围：
- 明确数据来源、服务绑定关系、快照元数据、恢复目标和失败后的状态。
- 提供 preview/确认语义，避免恢复操作覆盖错误工作区。
- 复用现有 sandbox、归档和路径校验；数据库管理入口继续走 Adminer 等外部服务纳管。

本轮不做：完整数据库 GUI、跨云同步、默认覆盖式恢复、一次支持所有数据库和中间件。

推荐阶段：
- Contract：明确一个数据来源的快照格式、服务绑定、目标和覆盖保护。
- Core：实现快照、校验、恢复和失败回滚；先使用本地 fake 数据源。
- Adapter/UI：接入预览、确认、列表和结果，不让前端拼接路径。
- Verify：覆盖损坏、空间不足、权限错误、取消、重复执行和敏感元数据。

完成条件：
- 快照可识别、可校验、可列出，并能恢复到明确目标。
- 快照损坏、版本不匹配、目标路径非法和空间不足都有可诊断结果。
- 恢复前后服务状态和数据边界明确，不把凭据写入快照元数据或日志。
- 对成功、取消、失败和重复执行有离线测试。

验证重点：路径 sandbox、原子性/部分失败、保留策略边界、权限错误、敏感数据处理和跨平台路径。
```

## 方向七：AI 原生运行时

```text
方向目标：让 AI 能在明确权限和安全边界内完成“检查环境、补齐依赖、启动工作区、等待就绪、
汇总错误并给出下一步”这一闭环；所有输出可脱敏、操作可审计，且不依赖 AI 猜测日志或主机状态。

建议首个切片：MCP 错误聚合与就绪等待，优先建立 AI 可可靠消费的状态闭环；环境供给和审计随后接入。

本轮范围：
- 提供只读的当前错误摘要、服务状态和等待就绪能力，支持明确超时和取消语义。
- 使用 core 已有健康、日志和错误来源，不让 MCP 自己解析未经结构化的原始输出。
- 为所有返回内容接入统一脱敏，并定义稳定错误码和结果 schema。

本轮不做：让 AI 直接执行任意 shell、把所有日志原样转发、无确认的高影响操作、一次完成全部 MCP 能力。

推荐阶段：
- Contract：定义错误聚合、等待、超时、取消和脱敏后的 MCP schema。
- Core：复用健康/日志/错误来源，生成按服务聚合的结构化结果。
- Adapter/UI：接入 CLI/MCP 工具，不绕过 core 直接读取原始日志。
- Verify：覆盖并发服务、状态竞态、超时取消、空错误、超长摘要和权限边界。

完成条件：
- AI 一次调用能判断工作区是否就绪，并获得按服务聚合的错误摘要。
- 等待超时、服务失败、服务被停止和无错误等状态可区分。
- token、密码、连接串和环境变量不会出现在工具输出、事件或审计记录中。
- MCP 合同、脱敏规则、超时/取消和 fake transport 均有测试。

验证重点：并发服务、状态竞态、超时取消、空错误、超长日志摘要、脱敏回归和权限边界。
```

## 方向八：多平台可用

```text
方向目标：让 Windows、macOS 和 Linux 都具备可持续验证的构建、测试、打包和核心运行能力，
并通过三平台冒烟验收收敛进程、路径、权限、通知和网关等差异，再对外承诺平台支持。

建议首个切片：先把 macOS/Linux 加入 CI 编译与测试矩阵；没有持续验证前，不急着宣称安装包可用。

本轮范围：
- 保留 Windows 现有构建与发布链路，新增 macOS/Linux 的最低可用 CI 检查。
- 盘点并修复本轮暴露的编译、测试、路径或条件编译问题。
- 为每个平台记录当前可验证的能力边界和明确失败原因。

本轮不做：同时完成签名、公证、所有安装包格式、完整真机验收和平台行为重构。

推荐阶段：
- Contract：确定各平台 CI 的最低编译、测试和允许跳过项。
- Core：修复 CI 暴露的条件编译、路径或进程问题，保持 Windows 行为不变。
- Adapter/UI：只处理被 CI 证明需要的最小平台适配。
- Verify：先稳定三平台 CI，再单独推进打包、签名和真机冒烟。

完成条件：
- 三个平台的核心 crate 能在 CI 中编译，离线测试按平台实际能力执行。
- 平台专属失败不会被吞掉，也不会破坏 Windows 发布链路。
- CI 结果能成为后续打包和真机冒烟的可靠前置条件。
- README/支持声明不超出实际验证范围。

验证重点：CI 矩阵、cargo fmt、core/CLI 测试、路径与进程分支、失败日志脱敏以及 Windows 回归。
```

## 方向九：长期与生态

```text
方向目标：在核心服务 kind、导入和工作区契约稳定后，建立可控的扩展边界，
逐步支持自定义 kind、WSL2、团队环境基线和社区模板，让生态能力建立在稳定契约上而不是提前固化错误抽象。

建议首个切片：先做扩展前置条件审计和契约稳定性结论；只有证据表明核心边界已稳定，才选择一个最小扩展原型。

本轮范围：
- 检查 kind、导入、工作区 spec、错误码和权限模型是否足以支撑扩展。
- 列出稳定契约、未决决策、兼容性风险和每个生态候选项的最小实验。
- 若条件满足，只实现一个隔离的自定义 kind 或模板导入原型，并定义退出/回滚路径。

本轮不做：在契约未收敛时引入插件 ABI、WSL2 后端、团队云协议或社区市场；不以抽象代码代替真实用例验证。

推荐阶段：
- Contract：审计 kind、导入、工作区 spec、错误码和权限模型的稳定性。
- Core：若审计通过，只实现一个隔离原型；否则只修复阻塞契约，不写生态代码。
- Adapter/UI：仅为真实原型提供最小入口，禁止提前铺设通用市场/插件界面。
- Verify：验证兼容性、未知 kind 行为、权限隔离、失败回滚和升级路径。

完成条件：
- 有一份基于现有代码和 spec 的扩展就绪结论，而不是主观判断。
- 每个未决问题都有影响范围和后续验证方式。
- 若实现原型，其失败不会污染核心 kind、IPC 或配置兼容性。
- 原型有最小测试、文档和明确的暂不承诺边界。

验证重点：兼容性、未知 kind 加载/启动行为、权限隔离、版本演进、失败回滚和文档是否会诱导过早使用。
```

## 完成后的维护动作

当一个候选项已经完整交付，不要只在本提示词的最终报告里写“完成”：

1. 行为契约进 `docs/spec/`。
2. 用户可感知的变化进 `CHANGELOG.md`。
3. 当前实现状态同步到 `docs/inventory/`。
4. 从 `docs/ROADMAP.md` 移除已交付候选项，或改写为仍未完成的剩余范围。
5. 保留本文件的方向目标；它描述的是长期执行边界，不随单个切片完成而删除。
