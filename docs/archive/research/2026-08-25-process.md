# 梳理过程（2026-08-25）

规划阶段第一份，故意写短。记录「怎么得出结论」，方便以后的 agent 不要重走弯路。

## 输入

用户要做一个可视化项目启动器，对标 DevPod / Taskfile / DevToys / Runme / Nix，但明确「都不是想要的」。清单有 17+ 条，1.0 只要 **Windows + Java（Spring Boot 多模块）+ Node**。

仓库 `<repository-root>` 当时是空的。

## 先拆诉求，再砍 1.0

把清单分成三层，否则会做成大而全的 DevOps 平台：

1. **工作台核心（1.0 必须真）**：导入项目、识别模块/脚本、YAML 描述服务、起停、端口/环境变量、日志、状态、打开目录。
2. **加速层（1.x 可做薄）**：模板、git clone、探测 JDK/Node（不负责装）。
3. **平台层（明确 2.x）**：云账号同步、一键迁移、AI、README 生成、nginx/apache、Docker 镜像、全语言工具链安装。

砍的原则：没有「进程还活着 + 日志能看」之前，装环境、AI、云同步都是空中楼阁。

## 竞品怎么用

不是做功能对照表然后全抄。按 **用户作业** 分类：

- 想「可复现环境」→ Nix / DevPod（我们 1.0 不抢）
- 想「写步骤」→ Taskfile / Runme（我们只吸收 YAML，不当 Notebook）
- 想「看一组服务」→ Dockge / IDEA / orckit（这才是 1.0 战场）

结论：产品一等公民是 **Workspace 里的长期 Service**，不是 Task，也不是 Container。

## 技术选型怎么收束

三个壳层都看过（Electron / Tauri / Wails）。过滤器只有用户自己写的约束：

- 轻 → 淘汰 Electron
- Windows 优先、WebView2 预装 → Tauri 和 Wails 都行
- 核心是进程树（尤其 Maven 子进程）→ 引擎用 Go 比 Rust 更合适，也避免 Tauri 再挂 Go sidecar

所以推荐 **Wails v2 + Go + Vue 3**，不是因为 Go 更时髦，而是进程监管、Job Object、管道、健康检查都在同一语言里。

备选记一笔：若团队坚决不写 Go，再改 Tauri 2 + Rust。不要 1.0 就双引擎。

## 配置格式

不兼容 Taskfile、不兼容 compose。原因：Taskfile 没有「服务」模型；compose 没有「本机 Spring 模块」。自己做一个很小的 `supertask.yaml`，看起来像 compose 的 services + 一点 task。

以后可以 **导入** Taskfile / compose / README，而不是一开始兼容全世界。
