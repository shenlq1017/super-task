## 一句话结论

- **地基对横向扩展友好**：`ServiceSpec.kind` 是 String + flatten extra（`spec/file.rs:72,126`），健康检查、指标、网关均与 kind 解耦；1.3 compose 是新增 kind 的完整先例。
- **成本集中在四处**：kind 字符串 match 散点（validate/launcher/scan）、`ToolchainProbe`/`ToolKind` 扩展、mise/winget 安装映射、扫描识别特征（现无 pyproject/go.mod）。
- **捷径存在**：`kind: generic`（argv 通用进程）自 1.0 预留未实现。
- **路线图位置**：Python/Go 排在 2.2「能长」（roadmap「版本地图」），提前 = 路线图重排，需显式决策。
- **入口调整是低风险项**：双注册表驱动导航，导出/导入是页面卡片级迁移，core 的 pkg/lock 不动。
- **v2.0 云客户端已进入 live/自动化状态，但服务端不是已验收能力**：`crates/supertask-cloud-server` 仍只有配置、认证/实体数据层与 SQLite migration 骨架；HTTP router/API、`/healthz`、配额/遥测 handler、集成测试以及真实端点运营仍待完成。详见 [cloud-server.md](../spec/cloud-server.md) 与 inv-4 §F。
- **易用性有现成候选池**：1.2 遗留的服务分组 UI（字段已留、UI 缺失）、Maven mirror/npm registry 运行时接线（半成品）、系统级崩溃通知。
