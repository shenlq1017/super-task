## 0. 策略前提

### 0.1 三条公理

1. **功能对等是底线，不是可选项。** 开源免费意味着不必靠「做别人没有的」取胜——
   竞品已有的成熟功能，能复刻的就复刻。功能一致不构成劣势，**缺失才是**。
2. **差异化是加分项。** 在竞品因架构或平台约束做不到处建立优势（尤其 Windows）。
3. **竞品的限制就是需求池。** 竞品公开记载的平台限制、付费墙、已删功能，
   等价于一份经过市场验证的需求清单。

### 0.2 定位：编排层为主，供给层取可用子集

- **编排层（主战场）**：把任何来源的服务——本机进程、compose、外部已装实例、WSL2、远程——
  收进同一张拓扑图，统一启停、健康、日志。各家模型都是「我起的服务我才管」，
  **没人做「不是我起的也能纳管」**，这是结构性空位，且与现有架构天然契合
  （kind 抽象、健康检查、日志聚合、进程树清理均为来源无关）。
- **供给层（取子集）**：不做 2000 包仓库。只做 ① 自举 ② 免安装归档 ③ 声明式需求。
  够覆盖高频场景即可。
- **能纳管的就不自建**：邮件捕获、对象存储、搜索引擎、数据库管理界面这类「开发依赖服务」，
  优先复用成熟开源件（Mailpit / MinIO / Meilisearch / Adminer），
  以 `generic` 或 `compose` 服务纳管，而不是自己写实现。

### 0.3 当前基座（已交付）

- Windows 安装包（NSIS / MSI）随 GitHub Release 发布，自动更新链路已验证
  （双端点：国内 cnb.cool 镜像 + 海外 GitHub Releases，发布说明注入更新弹窗）。
- 14 个功能页全部 Live：运行、日志、配置、模板、环境、工作区、发现、Git、容器、网关、系统监控、云、AI、设置。
- 六种服务 kind 可启动：spring-boot / node / compose / python / go / generic。
- 主机指标已采样并通过 `system.metrics` 暴露：CPU（含四分占比）、内存（含交换）、磁盘、
  CPU 温度、网络上下行速率与本机 IPv4；「系统监控」页提供实时面板与使用率历史。
- 服务监管：`restart` 策略（`never/on-failure/always` + `max_retries`）自动重启已交付；
  崩溃通知（Toast / 系统通知，窗口失焦时走系统通知）已交付。
- 孤儿进程纳管：发现页可把工作区目录下运行中的外部进程反推成 generic 服务草稿，
  dry-run 预览确认后写入 `supertask.yaml` 统一启停（`ipc.md` §10.16）。
- 桌面应用常驻守护，`stop` / `restart` / `status` / `logs` 随时可用。

## 1. 竞品限制 → 机会清单

> 来源为各竞品公开文档 / 仓库的一手约束，非推测。每一条都对应一个可占的位置。

### ServBay（最直接的对手，macOS + Windows，闭源付费）

| 事实 | 我们的机会 |
|---|---|
| 免费版限 **5 个站点 / 5 条 DNS 记录**，无自定义端口、无 CORS、无多域名别名、无网站分组 | 开源免费，无上限 |
| **hosts 文件管理、PKI、ACME、通配符与 SAN 证书、自动备份 仅 Pro** | 免费提供 |
| **内置邮件服务器 仅 Pro**（SMTP/POP3/SSL/STARTTLS/中继/Webhook） | 纳管 Mailpit 之类的开源件即可，成本极低 |
| **隧道 仅 Pro**（Cloudflared / FRP / Ngrok / Pinggy） | 把 cloudflared 当普通服务纳管，不需自研协议 |
| **Typesense / Meilisearch / MinIO 仅 Pro** | 同上，走纳管路线的边际成本几乎为零 |
| 团队管理 / 统一配置 / 虚拟开发网络 **Team 版 $399 起** | 开源自托管，零成本 |
| 闭源 | 开源可审计——「密钥不上云」的信任基础 |
| **MCP 已暴露 System Info & Metrics**，明确用途是让 AI 判断"还能不能起一个服务 / 是否适合跑大模型" | 数据我们已有，只差一个 MCP 工具 |

### orckit（CLI 编排，最像的直接对手）

| 事实 | 我们的机会 |
|---|---|
| `kill_orphan_ports` **仅 POSIX**（依赖 `lsof`） | **Windows 独家**：已有端口模块 + 进程树清理，能做到它做不到的 |
| 已删除 `stop` / `restart` / `status` / `logs`（缺 daemon） | 桌面应用**天然常驻**，这是架构优势，README 已明说 |
| MCP 只读，且明确警告「可能暴露含秘钥的进程输出」 | 有密钥模块，可做**输出脱敏**，安全即卖点 |
| 构建状态解析仅 webpack / angular | 可覆盖 Vite / Next / Nuxt，或做通用日志模式匹配 |
| 运行需 Node 20+ | Rust 单文件，零运行时依赖 |

### 其他

| 竞品 | 限制 | 机会 |
|---|---|---|
| Devbox | 依赖 Nix，Windows 支持弱 | 无需 Nix，Windows 优先，原生性能 |
| DDEV / Lando | 依赖 Docker | 宿主机原生，不引入容器层 |
| Docker Compose | 只排序不等就绪；Java 栈健康检查难写 | 健康通过才算起来（已有），且懂 Spring Boot |

**待补充**：竞品 issue 区的用户痛点尚未纳入。`gh auth login` 后可用
`gh api repos/<owner>/<repo>/issues` 批量拉取（orckit / devbox / ddev / overmind / pm2），
重点看高赞 feature request。上一轮尝试时 GitHub API 匿名配额被打满、issues 页面为 JS 渲染，
需登录后再试。

## 2. 评估口径

每个候选点按三维评级，最终落到优先级：

- **价值**：对目标用户（本机多服务开发者，尤其 Java + Node）的感知强度。
- **成本**：小 = 数据与结构已就绪，主要是接线；中 = 需要一个新模块；大 = 涉及平台权限或生态建设。
- **契合度**：与「宿主机编排层」定位的吻合程度。契合度低但价值高的，
  优先走**纳管**而不是自建。

评级记号：价值 ★★★ / ★★ / ★；成本 小 / 中 / 大；契合度 高 / 中 / 低。

## 3. 方向一：服务监管与自愈

> 主题：把「长期运行的服务」真正托管起来，而不只是拉起来。
> 这一块是对标 PM2 / orckit 的欠账，属于**不补就说不过去**的类别。

**目标：** 让每个服务都成为可持续托管的运行单元：能够按真实就绪状态纳入编排，
在启动、失败、重启和依赖变化时执行可预测的生命周期策略，并允许用户在异常后接管恢复。

| 候选点 | 来源 | 现状 | 价值 | 成本 | 契合 | 说明 |
|---|---|---|---|---|---|---|
| 日志模式就绪判定 | orckit `ready: log-pattern` | 健康检查仅 `none/tcp/http` | ★★★ | 中 | 高 | 匹配 `Started ... in ... seconds`；Spring Boot 主打场景的刚需，现在只能靠 tcp 猜 |
| 服务级生命周期钩子 | orckit 四个钩子带独立超时 | 只有工作区级 `scripts` | ★★ | 中 | 高 | `pre_start` 失败阻断；`post_start` 可用于安装依赖等慢操作 |
| 级联重启下游 | orckit | 拓扑数据已有，重启只作用于单个服务 | ★★ | 小 | 高 | 修好上游后一键重启传递闭包 |
| 失败保持与手动重试 | orckit `manual_retry` | 失败即自动清场 | ★★ | 中 | 高 | **这是设计取舍而非缺陷**，做成可选策略，默认保持现有清场行为 |

> 已交付移出：`restart` 策略与重试上限、崩溃通知（进 `CHANGELOG.md` 与 `docs/spec/yaml.md`）。

## 4. 方向二：纳管任意来源

> 主题：README 开篇叙事是「AI 起的服务没人收场」，当前产品给的唯一动作却是「杀掉它」。
> 方向二要把叙事兑现为「收编进来，由我统一启停」。

**目标：** 让本机已有的进程、Compose、Procfile、devcontainer 等服务来源都能先预览、
再以可追溯的方式纳入同一工作区拓扑，统一启停、健康检查、日志和冲突处理，而不是只能发现或终止。

| 候选点 | 来源 | 现状 | 价值 | 成本 | 契合 | 说明 |
|---|---|---|---|---|---|---|
| compose 导入 | compose 生态 | compose 已是受支持 kind，但无导入器 | ★★★ | 中 | 高 | 每个 service 转成一等公民服务，而非整包当一个 compose 服务 |
| Procfile 导入 | Overmind / Foreman / Heroku | 无 | ★★ | 小 | 高 | 格式极简，半天工作量，直接撬 Overmind 用户池 |
| devcontainer / `.env` 导入 | VS Code 生态 | 无 | ★★ | 中 | 中 | 顺带解决环境可复现的钩子 |
| 导入 dry-run 与冲突合并 | 现有 Taskfile 导入的 preview/apply 机制 | 机制已有，未复用到新导入器 | ★★ | 小 | 高 | 导入前可预览差异并逐项选择 |

> 已交付移出：**孤儿进程纳管**——发现结果 → generic 服务草稿的 dry-run 预览与冲突报告、
> 确认后写回 yaml（进 `CHANGELOG.md` 与 `docs/spec/ipc.md` §10.16）。草稿忠实复刻原命令行
> （`kind: generic` + program/args），不伪造专用 kind 字段；env OS 层不可得、恒为空。
> 剩余范围：运行中进程**原地接管**（免重启纳入引擎监管，当前靠「重开工作区识别为外部实例」衔接）、
> 专用 kind 的智能推断（仅当证据充分）。
| 反向导出矩阵 | Devbox「一份定义多处使用」 | 无 | ★★ | 中 | 高 | 导出 devcontainer.json / compose.yml / `.mise.toml`，把自己变成环境的通用翻译层 |

## 5. 方向三：环境供给

> 主题：打破「能探测、但装不了什么」的困境。**不做 2000 包仓库**，只做高频子集。

**目标：** 让工作区能够用声明式需求从已有环境、可用包管理器或免安装归档中补齐高频工具和中间件，
同时保持版本隔离、来源透明和失败可解释，使“从零准备并启动项目”成为可重复流程。

| 候选点 | 来源 | 现状 | 价值 | 成本 | 契合 | 说明 |
|---|---|---|---|---|---|---|
| **工具链自举** | Devbox 自动装 Nix；ServBay 开箱即用 | 优先 mise、winget 兜底，两者皆无则直接报缺失 | ★★★ | 中 | 高 | **没有包管理器就一条路都没有**——先打破鸡生蛋 |
| **免安装中间件归档** | ServBay 2000+ 包（取其子集） | 工具枚举只覆盖 9 个语言工具，**零中间件** | ★★★ | 大 | 高 | Postgres / Redis / MySQL / MinIO 等官方 zip 版，解压即用、免管理员权限。**10–20 个足够覆盖高频场景** |
| 声明式 `needs` | Devbox / compose 条件依赖 | resolve-only dry-run 已交付（ipc.md §10.17）：四态解析 + 接入 mise/winget 既有供给源；归档仅报告可供给性 | ★★★ | 中 | **极高** | `needs: postgres@16` → 自动发现本机 / 可安装，都不行就明确说清为什么。剩余：归档供给执行器、compose/docker 来源发现、项目级版本隔离联动 |
| 项目级版本隔离 | ServBay 项目级环境设定；mise | 工具链段是探测结果，非供给声明 | ★★ | 中 | 高 | 两个项目可分别钉 JDK 17 与 21 |
| 工具清单远端化 | ServBay 可升级包 | 版本是硬编码白名单 | ★ | 小 | 中 | 加一个工具不必发版 |
| **本地邮件捕获** | ServBay 内置邮件服务器（**仅 Pro**） | 无 | ★★ | **小** | 中 | 纳管 Mailpit / MailHog 即可。注册、找回密码、通知邮件的本地调试是刚需 |
| 对象存储与搜索引擎 | ServBay MinIO / Meilisearch / Typesense（**仅 Pro**） | 无 | ★ | 小 | 中 | 同上，走纳管路线，边际成本几乎为零 |

## 6. 方向四：网络与身份

> 主题：让 gateway 从「生成反代配置」升级为「本地服务真正可达」。
> ServBay 把 hosts 管理、通配符证书、自动备份放在付费墙后——我们免费提供。

**目标：** 让工作区服务在本机、局域网和受控的外部回调场景中都能稳定、可验证地访问，
统一处理域名解析、证书、反向代理、WebSocket、CORS 和隧道，同时不牺牲本地密钥与权限边界。

| 候选点 | 来源 | 现状 | 价值 | 成本 | 契合 | 说明 |
|---|---|---|---|---|---|---|
| 本机 DNS 与 hosts 管理 | ServBay dnsmasq（hosts 管理**仅 Pro**） | 无 DNS / hosts 能力，域名能否解析取决于系统 | ★★★ | 大 | 高 | 涉及权限提升，是成本最高的一项 |
| 私有 CA 与证书签发 | ServBay 私有 CA + ACME（通配符 / SAN **仅 Pro**） | 无签发代码，仅蹭 caddy 的 internal CA | ★★★ | 大 | 高 | 免费提供付费能力，是明确的卖点 |

> 已交付移出：**隧道 / 内网穿透**（cloudflared / frpc 以 generic 服务模板纳管，
> token 走 env_file，不自研协议）、**网关 WebSocket**（apache 补齐
> `upgrade=websocket`，三引擎一致）、**网关 URL 重写 / 重定向 / 静态站点**
> （`redirect` + `redirect_status`、`strip_prefix`、`static_dir` 整站静态）、
> **网关 CORS 与多域名别名**（route 级白名单回显 CORS + preflight 本地 204、
> host 逗号分隔别名组）（进 `CHANGELOG.md` 与 `docs/spec/yaml.md` §7.1）。
> 反代「能通 → 够用」的缺口已闭；剩余两项均为涉及平台权限的高成本项。

## 7. 方向五：主机与服务可观测性

> 主题：ServBay 有系统资源监控面板，且**通过 MCP 把系统与指标暴露给 AI**；
> 我们已有 `system.metrics` 采样，但只有状态栏一行，且未对 AI 开放。
>
> 已交付移出：**把主机指标暴露给 MCP**——`supertask_host_metrics` 只读工具
> （无参数、结构稳定、脱敏：无 IP/路径/进程/环境信息；复用既有采样，不持久化，
> 契约见 cli.md MCP 清单）。
>
> 已交付移出：**按服务归因的资源占用**——监控页「服务资源占用」卡片（各服务 CPU/内存/
> 进程数按内存降序，null 为「—」不伪造 0，compose/外部纳管行注明口径）+ 运行页服务卡片
> CPU 徽标。盘点勘误：per-service Job 采样（`metrics.snapshot`）此前已存在，
> 缺的是归因呈现，本切片零新采样面。
>
> 已交付移出：**系统信息面板**——监控页静态卡片（平台 / 系统版本 / 应用版本 /
> CPU 架构与核数 / 内存总量），新增只读 `system.info` 命令（平台 API 直采、零新增依赖、
> 取不到为 null；纯静态，与动态指标分列）。
>
> 已交付移出：**指标历史趋势**——监控页「历史趋势」卡片（CPU + 内存压力面积图，
> 跨页面存活、有界约 1 小时环形缓冲）。复用状态栏与监控页既有 `system.metrics` 轮询
> 去重合并，零新采样面；**不落盘**，「不持久化」约定不变，跨重启持久化保留为显式
> 扩展选项。
>
> 已交付移出：**一键体检报告**——监控页「体检报告」卡片（工具链 / 网关引擎 / Docker
> 三节只读探测 + Markdown 导出，复用既有探测面零新采样，口径同 CLI `supertask doctor`）。
> 盘点勘误：「服务列表版本/PID 列」现状描述过时——PID / 状态 / 快速启停运行页均已交付，
> 剩余「版本」需 spec `version:` 字段扩展，已改写为表中剩余候选。

**目标：** 把主机和服务运行状态变成可追溯、可归因、可供人和 AI 使用的诊断上下文，
能够回答“哪里在消耗资源、何时开始异常、当前是否适合启动新服务”，并提供可导出的体检结果。

| 候选点 | 来源 | 现状 | 价值 | 成本 | 契合 | 说明 |
|---|---|---|---|---|---|---|
| 服务版本标注（spec 扩展） | ServBay 服务控制面板 | 勘误：状态 / PID / 快速启停运行页均已交付（PID 在服务卡片与详情多处显示）；「版本」无声明来源——服务是用户应用而非受管中间件 | ★ | 中 | 高 | 需 spec `version:` 字段矩阵（schema/校验/编辑器/测试），非接线范畴 |

## 8. 方向六：数据与备份

**目标：** 让与服务绑定的开发数据具备低门槛、可验证的快照与恢复能力，
支持工作区级定时保留和外部目录备份，同时通过纳管成熟工具满足数据库管理，而不自建完整数据库 GUI。

| 候选点 | 来源 | 现状 | 价值 | 成本 | 契合 | 说明 |
|---|---|---|---|---|---|---|
| 服务关联库的快照 / 恢复 | ServBay 数据库备份（**仅 Pro**） | 数据卷级离线快照/恢复已交付（spec `data:` 段 + `.supertask/snapshots`，ipc.md §10.18）；**数据库感知**的备份（在线/逻辑 dump、seed、常用查询）仍无 | ★★★ | 大 | 高 | 剩余最小集：seed、快照、恢复、常用查询中「数据库感知」的部分；文件级快照已能覆盖 SQLite/H2 等单文件库的离线场景 |
| 数据库管理入口 | ServBay 内置 phpMyAdmin / Adminer | 无 | ★★ | **小** | 中 | **不自建 DB GUI**，纳管 Adminer 并在服务卡片上给一个「打开」按钮 |
| 工作区定时备份与保留策略 | ServBay 自动备份（**仅 Pro**） | 只有手动导出 zip；快照归档机制已就绪（共用 `snapshot.rs`），缺定时触发与保留策略 | ★★ | 中 | 高 | 与快照能力共用一套归档机制 |
| 备份到外部目录 | ServBay（**仅 Pro**） | 无 | ★ | 小 | 中 | 配一个目录即可（快照目录当前钉在工作区 `.supertask/snapshots/`） |

## 9. 方向七：AI 原生运行时

**目标：** 让 AI 能在明确权限和安全边界内完成“检查环境、补齐依赖、启动工作区、等待就绪、
汇总错误并给出下一步”这一闭环；所有输出可脱敏、操作可审计，且不依赖 AI 猜测日志或主机状态。

| 候选点 | 来源 | 现状 | 价值 | 成本 | 契合 | 说明 |
|---|---|---|---|---|---|---|
| MCP 环境供给能力 | ServBay MCP 能装包、建站、查库 | MCP 只有运行控制类工具 | ★★★ | 中 | 高 | `ensure_tool` / `ensure_service`，让 Agent 说一句「跑起这个项目」就能补齐依赖 |
| MCP 错误聚合与就绪等待 | orckit MCP `get_errors` / `wait_for_build` | 已交付（MCP `supertask_errors` / `supertask_wait_ready`，cli.md；outcome 区分 reached/failed/stopped/timeout，超时是结果不是错误） | ★★★ | 小 | 高 | AI 一次调用拿到「当前栈是否就绪 + 按服务聚合的错误摘要」 |
| MCP 输出脱敏 | orckit 明确警告可能泄露密钥 | 已交付（MCP 全工具出口统一过 `ai::sanitize::Redactor`：声明密钥值替换 + 敏感行整行掩码，幂等） | ★★★ | 小 | 高 | **安全即卖点**，且是竞品的公开短板 |
| 环境快照上下文 | 自有 | 无 | ★★ | 中 | 高 | 把工具版本、端口、健康、错误摘要结构化输出给 AI |
| AI 操作审计与回放 | 自有 | 无 | ★★ | 中 | 高 | 可查看「AI 这段时间动了什么」并回滚 |

## 10. 方向八：多平台可用

> 现状：**只有 Windows 有构建产物和 CI**。引擎含 Unix 分支，
> 但 macOS / Linux 既无产物、也无 CI 覆盖与真机验证，因此 README 不承诺可用。

**目标：** 让 Windows、macOS 和 Linux 都具备可持续验证的构建、测试、打包和核心运行能力，
并通过三平台冒烟验收收敛进程、路径、权限、通知和网关等差异，再对外承诺平台支持。

| 候选点 | 现状 | 价值 | 成本 | 说明 |
|---|---|---|---|---|
| CI 覆盖 macOS / Linux | CI 矩阵仅 `windows-latest` | ★★★ | 小 | **应先做**：不产出安装包，也要先保证编译与测试通过，否则后面全是盲改 |
| 产出 macOS（Apple Silicon + Intel）与 Linux 构建 | 发布流程只有 Windows 任务 | ★★★ | 中 | 发布流程加两个任务；更新检测端点已按平台通用，无需改 |
| macOS 签名与公证 | 无 | ★★★ | 中 | 未签名的包会被 Gatekeeper 拦下，等于不可用；需要开发者账号 |
| Linux 打包分发 | 无 | ★★ | 中 | 建议 AppImage 作为自动更新通道（deb / rpm 不适合就地自更新） |
| 三平台真机冒烟 | 从未做过 | ★★★ | 中 | 起停、进程树清理、健康检查、日志、端口回收、通知与托盘，六项 |
| 平台差异收敛 | 进程与探测已有平台分支 | ★★ | 中 | 路径约定、权限模型、caddy / nginx 安装方式与命令行差异 |

## 11. 方向九：长期与生态

**目标：** 在核心服务 kind、导入和工作区契约稳定后，建立可控的扩展边界，
逐步支持自定义 kind、WSL2、团队环境基线和社区模板，让生态能力建立在稳定契约上而不是提前固化错误抽象。

| 候选点 | 来源 | 价值 | 说明 |
|---|---|---|---|
| 插件 / 自定义 kind | 原 2.2 规划 | ★★ | 抽象未收敛前不做，避免把错误的抽象固化成契约 |
| WSL2 后端 | 原 2.2 规划 | ★★ | Windows 上跑 Linux 工具链；等 Windows 主场景被真机验收后再投入 |
| 团队环境基线与漂移检测 | ServBay Team 版 | ★★★ | **云的重新定位**：从「备份同步」升级为「标准环境下发 + 版本漂移检测」，价值高一个量级。定位未拍板前不投入 |
| 模板生态 | 自有 | ★ | 内置模板之外，支持社区模板的导入与分享 |

## 12. 明确不做

- **自建 2000+ 包仓库**：个人项目硬碰成熟商业产品不现实。取 10–20 个高频中间件，
  其余一律走**纳管**路线。
- **完整数据库 GUI**：DBeaver / Navicat 的地盘。只做与服务绑定的最小操作与入口跳转。
- **容器运行时与 K8s 编排**：Tilt / Skaffold / Garden 的地盘，与「宿主机优先」哲学冲突。
- **自研隧道协议 / 邮件服务器 / 搜索引擎**：全部复用成熟开源件并纳管。
- **云生产化**：定位（团队同步协议 vs 官方服务）未拍板前投入是沉没成本。

## 13. 优先级速览

按「价值 ÷ 成本」，并把契合度作为加权：

| 优先级 | 候选点 | 理由 |
|---|---|---|
| **最高** | MCP 暴露主机指标、MCP 输出脱敏 | 数据或结构已就绪，主要是接线；其中多项直接命中竞品的公开短板 |
| **高** | 日志模式就绪判定、compose 导入、MCP 错误聚合与就绪等待、CI 覆盖多平台 | 补主梁与欠账，工程量可控 |
| **高** | 系统信息面板、按服务资源归因 | 与「本机编排」定位高度契合，且是诊断价值最高的一类 |
| **中** | 工具链自举、声明式 `needs`（needs 解析已交付，剩归档供给执行器）、免安装中间件归档、项目级版本隔离 | 打开「从零准备环境」的能力，投入较大但决定能力上限 |
| **中** | 服务级钩子、级联重启、拓扑视图、Procfile / devcontainer 导入、导出矩阵 | 差异化与叙事兑现 |
| **中** | 本机 DNS、私有 CA、证书签发 | 价值高但成本也高，涉及平台权限 |
| **低** | 数据快照、定时备份、数据库入口、对象存储与搜索引擎纳管 | 主场景之外，或已有外部工具可替代 |
| **暂缓** | 插件 / 自定义 kind、WSL2、云生产化、模板生态 | 抽象未收敛或定位未定 |
